# Auto Dump Bot 🤖

**협동로봇 기반 아파트 음식물 쓰레기 무인 배출·세척 시스템**

주민이 전용 수거통을 거치대에 놓기만 하면, 협동로봇이 통을 파지해 RFID 수거함에 배출하고 물 세척까지 마쳐 되돌려주는 '손에 묻지 않는 24시 스마트 무인 수거 시스템'입니다.

> 두산로보틱스 ROKEY 부트캠프 8기 · 협동 1 프로젝트 | TEAM B-4 (구나영 · 박선욱 · 박채송 · 이현민)

- 비상정지 복구 로직 — 체크포인트 기반 12개 분기 복구 시퀀스

## 🏗️ 시스템 아키텍처

![System Architecture](code/robot_ws/src/auto_dump_robot_pkg/docs/diagrams/01_architecture.png)

3개 레이어가 유기적으로 연동됩니다.

| 레이어 | 기술 | 역할 |
|---|---|---|
| **HMI** | Tkinter (관리자) / Web (사용자) | 공정 상태 표시, 모드 선택, 비상정지, 실시간 모니터링 |
| **Backend** | FastAPI · WebSocket · SQLite | 명령 라우팅, 상태 브로드캐스트, 작업 이력 로깅 |
| **Robot** | ROS2 Humble · Doosan M0609 · OnRobot RG2 | 모션 제어, 센서 피드백, 안전 감시 |

### 이기종 통신 브릿지 설계

ROS2(스레드)와 FastAPI(AsyncIO)는 실행 모델이 다릅니다. 이를 **`asyncio.Queue` 기반 Producer-Consumer 패턴**으로 중재했습니다.

```
ROS2 Callback → asyncio.Queue → Background Task → ConnectionManager.broadcast() → HMI
```

`RobotBridge`는 큐 적재만 담당하고 웹소켓·HTTP API와 완전히 분리되어, 스레드 경계를 명확히 하고 비동기 I/O 병목을 해소했습니다. 큐에 `maxsize=1000`을 지정해 메모리 폭주도 방지했습니다.

## ⚙️ 공정 시퀀스

### 배출 단계

| 단계 | 동작 | 비고 |
|---|---|---|
| 1. Pick | 수거통 상단 테두리(Rim) 압착 파지 | V자형 물리 가이드로 위치 고정 |
| 2. Move | RFID 수거함 개폐 신호 연동 후 이동 | |
| 3. Tilt | 관절 기울임 | 모드 1: 45° / 모드 2: 60° |
| 4. Shake | Tool **Y축** 왕복 궤적 제어 | 모드 1: 진폭 5 × 8회 / 모드 2: 진폭 8 × 10회 |
| 5. Return | 수평 복귀 후 세척 위치 이동 | |

### 세척 단계

세척 지그 안착 → 밸브 조작 급수 → Tool **X축** 주기 운동으로 세척 → 완전 전도 배수 → 원위치 복귀

배출은 Y축, 세척은 X축으로 회전축을 분리했습니다. 통의 기울어진 자세가 서로 달라, 같은 축으로 흔들면 내용물이 한쪽으로만 쏠리기 때문입니다.

## 🛡️ 안전 설계 (핵심 차별점)

로봇 코드 1,733줄 중 **절반 이상이 예외 처리와 복구 로직**입니다. 정상 동작보다 "중간에 멈췄을 때 어떻게 되돌아오는가"가 더 어려운 문제였습니다.

### 1. 상시 안전 감시

일반적인 `movej`/`movel`은 동작이 끝날 때까지 블로킹되어, 이동 중 비상정지를 누르면 **현재 동작이 완료된 뒤에야** 멈춥니다. 통을 든 채 기울어진 상태로 정지하면 내용물이 쏟아집니다.

이를 해결하기 위해 **비동기 이동 + 짧은 주기 폴링** 구조로 전환했습니다.

```
safe_movej / safe_movel  →  비동기 모션 시작
                         →  도착까지 짧은 주기로 safety_watch() 호출
                         →  비상정지 플래그 · 외력 크기 · 파지 상태 감시
                         →  이상 감지 시 즉시 QSTOP (실패 시 QSTOP_STO 재시도)
```

단순 대기(`safe_wait`)조차 잘게 쪼개어, 감시가 끊기는 구간을 없앴습니다.

### 2. 체크포인트 기반 복구

![Reset Recovery](code/robot_ws/src/auto_dump_robot_pkg/docs/diagrams/03_reset_recovery.png)

비상정지 후 "무조건 홈으로 복귀"는 위험합니다. 통을 든 채 홈으로 가면 내용물이 쏟아지고, 세척 지그 근처에서 직선 복귀하면 구조물과 충돌합니다.

그래서 공정 진행 상태를 `RecoveryStage` 체크포인트로 기록하고, **마지막 체크포인트 + 실제 파지 여부**를 조합해 복구 경로를 분기했습니다.

| 정지 시점 | 복구 동작 |
|---|---|
| 파지 실패 | 통 내려놓기 없이 파지 위치 이탈 후 홈 |
| 배출 중 (기울어진 상태) | 수평 자세 복원 → 경유점 → 홈 |
| 통 파지 상태 | 원위치에 안전 하강 후 홈 |
| 세척 지그 주변 | 접근 위치 경유 → 경유점 → 홈 (구조물 충돌 회피) |
| 밸브 조작 중 | 밸브 열기/닫기 완결 → 밸브 해제 → 경유점 |
| 세척수 잔류 | 배수 위치로 이동해 잔수 배출 후 복귀 |

체크포인트는 스레드 락으로 보호되며, `/robot/recovery_stage` 토픽으로 발행되어 HMI가 배출 완료 전후를 구분해 버튼과 화면을 전환합니다.

### 3. 재파지 후 공정 재개

![Retry Pick](code/robot_ws/src/auto_dump_robot_pkg/docs/diagrams/05_retry_pick.png)

초기 파지에 실패해도 공정 전체를 폐기하지 않습니다. 통을 재파지한 뒤 남은 공정을 이어서 수행합니다.

## 💡 Lesson & Learn

**정상 동작을 만드는 것보다, 실패를 정의하는 것이 어렵다**
초기에는 공정 순서만 구현하면 될 거라 생각했습니다. 실제로는 "어디서 멈출 수 있는가"를 먼저 정의해야 복구 로직을 설계할 수 있었고, 이 관점의 전환이 프로젝트의 가장 큰 배움이었습니다.

**요구사항 정의가 코드 구조를 결정한다**
기획 단계에서 작성한 추적성 매트릭스(Req ID ↔ 구현 함수 ↔ Test Case)가 개발 중 판단 기준이 되었습니다. 기능 추가 요청이 있을 때 "이건 어떤 요구사항에 대응하는가"를 먼저 확인하는 습관이 생겼습니다.

**형상관리는 실력이 아니라 습관이다**
초기에 커밋 이력 관리를 소홀히 해 작업 기록이 남지 않았습니다. 이후 프로젝트에서는 개인 계정 커밋, 커밋 메시지 컨벤션, 브랜치 전략, 테스트 코드 작성을 직접 관리하고 있습니다.
